# C03 — عقد الخادم والدخول (طبقة Core)

آخر تحديث: 22 أكتوبر 2026. هذه الشريحة **عقد منطقي في `BunnListCore` مختبَر على Linux**، لا خادمًا فعليًا. نقاط الخادم وربط التطبيق وإبطال رموز Apple على بوابة الخادم/Mac.

قرارات معتمدة: الدخول بثلاث طرق (Apple + Google + بريد OTP)؛ **حد عمر التسجيل 16+** (قابل للضبط، يُراجع مع مختص قبل النشر).

## ما نُفّذ واختُبر في Core

| العقد | الملف | القاعدة |
|---|---|---|
| هوية المزود وحلّها | `Auth.swift` — `AuthIdentity`, `IdentityDirectory` | الحل بـ(provider, subject) فقط. لا دمج حسابين بالبريد وحده، وبريد Apple المخفي ≠ Google |
| ربط الهويات | `IdentityDirectory.link` | يتطلب جلسة متحقّقة للحساب + إثبات الهوية الثانية؛ يرفض هوية مرتبطة بحساب آخر |
| رمز البريد | `Auth.swift` — `EmailOTPService` | رد محايد لا يكشف وجود البريد، انتهاء ١٠ د، ٥ محاولات، تهدئة إعادة إرسال ٣٠ ث |
| الجلسات والرموز | `Session.swift` — `RefreshTokenFamily` | تخزين مجزّأ (hash)، تدوير، كشف إعادة الاستخدام يُبطل العائلة، انتهاء صلاحية |
| بوابة العمر والشروط | `AccountPolicy.swift` — `AgeGate(16)`, `TermsAcceptanceState` | قبول نسخة الشروط الحالية شرط للنشر |
| عدم التكرار | `APIContract.swift` — `IdempotencyStore`, `IdempotencyKey` | نفس المفتاح والحمولة → إعادة؛ حمولة مختلفة → 409؛ انتهاء المخبّأ يُبقي هوية المورد؛ المحذوف لا يُعاد |
| نموذج الأخطاء | `APIContract.swift` — `APIError` | 401/403/409/422/429 |

22 اختبار C03 ضمن 88 اختبار Core (صفر إخفاق، صفر تحذيرات، Swift 6.0.3).

## معلّق على بوابة الخادم/Mac (ليس ضمن هذه الشريحة)

- نقاط API الفعلية (v1) وربطها بالتطبيق، وشاشات الدخول في SwiftUI.
- تسجيل دخول Apple الحقيقي و**إبطال رموزه عبر خادمه** عند حذف الحساب (Guideline 5.1.1).
- `DeviceToken` وجلسات Keychain على الجوال.
- اتصال metadata قراءة-فقط لمخطط الإنتاج للتحقق من تطابق DTO.
- حسم نسخة الشروط وسياسة المجتمع ورقم حد العمر النهائي مع مختص.

## خطة ترحيل المنتج/الدفعة (تُنفّذ على الخادم في C03، ليست الآن)

المخطط الحالي (`bunnlist/prisma`) فيه `CoffeeLot` فقط بلا `CoffeeProduct` ولا موسم (راجع [schema-review.md](schema-review.md)). الخطة:
1. لكل `CoffeeLot` حالي يُنشأ `CoffeeProduct` أب، وتُنشأ له دفعة `UNKNOWN` واحدة معتمدة.
2. تُربط الدفعة الحالية بالمنتج، وتبقى تقييماتها (`Review` ← تقييم محصول، upsert فريد لكل مستخدم ودفعة).
3. لا تُحوّل المراجعات التاريخية إلى تجارب تلقائيًا؛ التجارب كيان جديد.
4. يُطبّق على نسخة معزولة مع خطة استعادة قبل الإنتاج. لا `seed`/`migrate` على الإنتاج.
